# Homogeneous Query Keys

## Motivation

The `Db` is the incremental query database at `virdant/src/db.rs`. Today its
keys are the heterogeneous `Query` enum (generated by `queries!` in
`macros.rs`), stored in `self.map: Mutex<IndexMap<Query, CachedVal>>`
(`guts.rs:13`). This heterogeneity creates two real ergonomic gaps:

1. **No dynamic enumeration.** The set of *materialized* queries is an opaque
   `HashMap` keyed by heterogeneous tagged values. There is no public way to
   iterate all live queries, or even all queries of a given kind, even though
   the data is all present (see the trace dump in `json.rs` / `graphviz.rs`
   which already walk `self.map`).

2. **No static dependency calculation.** Dependencies are only recorded at
   *runtime*, when a `Builder` calls `self.get(...)` on another query
   (`macros.rs:46`). The `deps: Vec<Query>` stored per cached value
   (`guts.rs:25`) is a vector of heterogeneous tagged values. There is no way
   to represent the dependency relation as a compact, statically-shaped table,
   and no way to derive a conservative dependency matrix without executing the
   build functions.

The root cause of both problems is that the query **key** is heterogeneous
*in shape*: each variant carries its own bespoke payload type. This plan
collapses the runtime key into a **homogeneous** fixed-width representation
while preserving full type safety at every public boundary via macro-generated
typed wrappers.

## Design

### Homogeneous runtime key

Replace the heterogeneous `Query` enum used for *storage* with a single fixed
-width key:

```rust
pub(crate) struct QueryKey {
    kind: u16,          // discriminator = numeric enum tag
    args: [Scalar; 3],  // bounded vector of scalar arguments
    fill: u8,           // how many args are actually set (0..=3)
}
```

- **Numeric enum for the query kind** — closed at compile time, cheap, and the
  natural index into any per-kind table (e.g. a per-kind map, or a
  `[u64; n]` dirty-bitmap).
- **Bounded scalar argument vector** — every query takes 0–3 arguments, and in
  practice every current argument is already a small index/id: `PackageId`,
  `SymbolId`, `ComponentId`, `Location`, `InternedString`, `ExprRoot` (see the
  declaration block at `db.rs:43-79`). These collapse to words.

### The `Scalar` trait

Introduce a small marker/transport trait that every query-argument type
satisfies. The important property is "is a stable, small, hashable ID":

```rust
pub(crate) trait Scalar: Copy + PartialEq + Eq + Hash + Into<u32> {
    fn to_scalar(self) -> u32;
}
```

Implemented for all existing argument types (and backed by their stored raw
`u32` where applicable). `QueryKey` derives `Clone, Debug, PartialEq, Eq,
Hash`, giving us exactly one hasher / comparison impl across all query kinds —
the uniformity that enables iteration, bitmaps, and dependency tables below.

### Type safety: keep it, via macro-generated wrappers

The caller-facing API must not regress. The `db_getter!`/`queries!` macros
(`macros.rs`) are the exact seam: today they map a typed getter onto a
heterogeneous enum value; tomorrow they map the same typed getter onto a
homogeneous `QueryKey`. The type-erasure to `u32` happens *only* inside
macro-generated code, never in user build functions.

```rust
pub(crate) struct ComponentAnalysisKey(pub(crate) QueryKey);
```

Per-query newtypes prevent passing the wrong argument type (a `PackageId`
cannot be used where a `SymbolId` is expected), while each query gets a checked
constructor that downcasts its typed args into the homogeneous key:

```rust
impl Db {
    #[track_caller]
    pub fn get_component_analysis(&self, symbol_id: SymbolId) -> Arc<ComponentAnalysis> {
        let key = QueryKey {
            kind: KIND_COMPONENT_ANALYSIS,
            args: [symbol_id.to_scalar().into(), ScalarKind::unset(), ScalarKind::unset()],
            fill: 1,
        };
        cast!(self.get_or_build(key, *caller), ComponentAnalysisKind)
    }
}
```

Because each public argument type implements `Into<Scalar>` and the per-kind
newtype is generated with the correct argument order, misuse is a compile-time
error. The storage layer sees only `QueryKey`; the type system sees typed
wrappers. Two layers, decoupled:

- **Layer 1 (homogeneous):** `QueryKey` + `[Scalar; 3]` — what the map, the
  deps vector, iteration, and any dependency matrix operate on.
- **Layer 2 (typesafe):** per-query newtypes + typed getters generated by
  `db_getter!` — the caller's experience is unchanged.

`cast!` (and a debug-assert invariant in the macro) guarantees a given kind's
newtype never carries the wrong argument type into storage.

## Resulting benefits

1. **Enumerability.** All query keys are the same shape, so the map becomes
   indexable/iterable freely. Exposing a public "all live queries" / "all
   queries of kind X" API becomes trivial, and is cheap enough to build tooling
   on (completing what the trace/`json.rs`/`graphviz.rs` dumps already reach
   for).

2. **Static dependency representation.** With a numeric kind + known argument
   arity, the *shape* of the dependency relation is fixed at compile time.
   The per-key `deps` become a small fixed vector (or a bit-packed set), and a
   dependency matrix `[n_kinds] × [n_kinds]` is representable as a fixed
   `[u64; n]` bitmask — a table you can precompute the size of, rather than an
   emergent runtime hash structure. This is the necessary precondition for
   deriving a *static* (conservative) dependency matrix by scanning build
   function call sites (`builder.get_*`).

3. **Space / cache efficiency.** Each key is a few words; the map is
   cache-friendly. One shared `PartialEq`/`Hash` impl instead of per-enum
   derivation (`macros.rs:20`).

4. **Cheaper invalidation.** `is_dirty_inner` (`guts.rs:128`) today walks
   `HashMap`s. A homogeneous key enables per-kind maps and dirty-bitmaps
   instead of full hash walks.

## Tradeoffs

- **Loss of per-argument static safety in the storage layer.** Safety is
  enforced by the *macro-generated constructors*, not by the storage type.
  Acceptable: it is a one-line invariant in the macro, and `cast!` + debug
  asserts catch violations.
- **Fixed argument count (~3).** Zero/low-arg queries waste a little space in
  the `[Scalar; 3]` vector. This is the classic uniformity trade, and a `fill`
  byte keeps the unused slots well-defined.
- **Rework of existing storage and dirty logic.** `guts.rs` (`Db` struct,
  `get_or_build`, `is_dirty`), `macros.rs` (`queries!`, `dispatch_build!`,
  `db_getter!`), and `db.rs` (the declaration block + dispatch table) all need
  rework. The *semantics* — rev-counter invalidation at `guts.rs:194-233` —
  stay identical.
